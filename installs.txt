# ============================================================
#  Council AI — Quick Install
#  Pick ONE of the sections below based on your hardware, then run
#  every line in that section in order. Each section is self-contained.
#
#  WHY MULTIPLE SECTIONS:
#  - Different NVIDIA architectures need different PyTorch CUDA wheels.
#  - llama-cpp-python (the GGUF runtime) defaults to a CPU-only build
#    when installed bare from PyPI. Each GPU section pulls the matching
#    CUDA-enabled wheel via --extra-index-url so the LLM actually runs
#    on your GPU.
# ============================================================


# NOTE on dream3dnx / SIMPLNX:
#   Only SECTION E (Linux + dream3dnx) installs dream3dnx. Sections
#   A / B / C / D (Windows-native) and SECTION F (WSL without
#   dream3dnx) all skip it because:
#     - dream3dnx is conda-only with no PyPI wheel
#     - it forces Python 3.12 and a numpy<2.x ABI pin
#     - the Dream3D pipeline-execution features silently degrade
#       cleanly without it (the JSON pipeline parser, vault index,
#       and pipeline scanner all still work — only simplnx-driven
#       execution is unavailable)
#   If you need full Dream3D pipeline EXECUTION on Windows, run
#   Section E inside WSL2 (it includes dream3dnx). If you want the
#   GPU-accelerated Council experience inside WSL WITHOUT dream3dnx
#   (same as Windows Sections B/C/D, just running on Linux),
#   use SECTION F.

# ============================================================
#  SECTION E — Linux with NVIDIA GPU + dream3dnx (full SIMPLNX support)
#  This is the ONLY section that includes dream3dnx. Run it on
#  native Linux (Ubuntu / Debian / Fedora / Arch) or WSL2 when you
#  want full Dream3D pipeline execution alongside GPU-accelerated
#  inference and the rest of the Council app.
#
#  Cards: any NVIDIA card supported by recent drivers (Turing through
#         Blackwell). The conda + pip lines below default to cu124
#         which covers RTX 40-series + most modern hardware. If you
#         have an older card needing cu121 or a Blackwell card
#         needing cu128 nightly, swap those two URLs accordingly
#         (the GPU-architecture-to-CUDA mapping in Sections B/C/D
#         applies identically on Linux).
#
#  Why Linux is the only platform that gets dream3dnx:
#  - dream3dnx requires Python 3.12 + numpy<2.3 ABI; on Windows that
#    conflicts with the wheels for several other deps the bundle
#    needs. On Linux the conda-forge channel resolves cleanly.
#  - The HDF5 / numpy ABI dance is what made Windows + dream3dnx
#    fragile. Linux distros + conda-forge handle it without the
#    MSVC redist / Visual Studio runtime mismatches Windows hits.
#  - WSL2 lets a Windows user opt in to this section without
#    leaving their laptop — boot WSL, follow Section E, and you
#    get dream3dnx execution in a Linux env with GPU passthrough.
#
#  Supported distros:
#    Ubuntu 22.04 LTS, 24.04 LTS
#    Debian 12 (Bookworm)
#    Fedora 39 / 40
#    Pop!_OS 22.04 / 24.04
#    Arch (current)
#    WSL2 with Ubuntu 22.04+ on Windows 10 build 19044+ / 11
# ============================================================
#
#  ── STEP 1: Install the NVIDIA driver (native Linux ONLY) ──
#  Skip this entire step on WSL2 — WSL inherits the Windows-side
#  driver. You only install the driver INSIDE Linux when Linux is
#  the OS booted directly on the hardware.
#
#  Ubuntu / Debian / Pop!_OS (recommended path — apt-managed
#  drivers survive kernel updates cleanly):
#      sudo apt update
#      ubuntu-drivers devices                     # shows recommended driver
#      sudo apt install nvidia-driver-550         # or whatever is recommended
#      sudo reboot
#      nvidia-smi                                  # should print the GPU table
#
#  Fedora:
#      sudo dnf install akmod-nvidia xorg-x11-drv-nvidia-cuda
#      sudo reboot
#      nvidia-smi
#
#  Arch:
#      sudo pacman -S nvidia nvidia-utils
#      sudo reboot
#      nvidia-smi
#
#  ── STEP 2: WSL2 ONLY — enable GPU passthrough ──
#  On Windows host, make sure WSL2 is up to date:
#      wsl --update
#  Inside WSL (Ubuntu shell):
#      nvidia-smi
#  If the table prints, GPU passthrough works.
#
#  ── STEP 3: Install conda (if not already) ──
#  Miniforge is the lightest path (conda + conda-forge by default):
#      wget https://github.com/conda-forge/miniforge/releases/latest/download/Miniforge3-Linux-x86_64.sh
#      bash Miniforge3-Linux-x86_64.sh
#      source ~/.bashrc

#  Adjust the cu124 in the torch + llama-cpp URLs if you have an

#  SECTION F — WSL2 with NVIDIA GPU (no dream3dnx)
#  Use this when you want the GPU-accelerated Council experience
#  from inside WSL — same as Windows Sections B / C / D, just
#  running on an Ubuntu shell with Windows-side GPU passthrough
#  via the NVIDIA driver you already installed on the host.
#
#  Why use WSL instead of Windows native:
#    - Smoother dependency resolution (apt + pip on Linux usually
#      has fewer wheel conflicts than the Windows wheel index).
#    - Native bash for any pipeline scripting you build around the app.
#    - llama-cpp builds from source cleanly if a CUDA wheel isn't
#      available for your specific stack.
#    - Same GPU as the Windows host — no second machine needed.
#
#  Why NOT WSL:
#    - Tkinter GUI requires WSLg (Windows 11) or an X server bridge
#      on Windows 10. WSLg works out of the box on Win 11 22H2+.
#    - No audio passthrough — the speech / mic tabs are read-only
#      inside WSL.
#    - File I/O across the /mnt/c boundary is ~10x slower than
#      keeping the vault inside the WSL filesystem (~/vault/).
#
#  If you ALSO need dream3dnx pipeline execution, use SECTION E
#  instead (same WSL prep, plus the conda dream3dnx step).
# ============================================================
#
#  ── STEP 1: Windows host — install WSL2 + NVIDIA driver ──
#  WSL2 inherits GPU access from the Windows-side NVIDIA driver;
#  you do NOT install a Linux NVIDIA driver inside WSL. Just make
#  sure the Windows driver is recent.
#
#  In an admin PowerShell:
#      wsl --install -d Ubuntu-22.04          # if WSL isn't set up yet
#      wsl --update                             # refresh WSL kernel
#  Then reboot, sign in to the Ubuntu user, and continue inside WSL.
#
#  Verify the Windows-side driver inside WSL:
#      nvidia-smi

#  Windows NVIDIA driver from https://www.nvidia.com/Download then
#  run `wsl --shutdown` from Windows and reopen the Ubuntu shell.
#
#  ── STEP 2: WSL2 — install build tools + audio libs ──
#  WSL Ubuntu ships minimal; a few system packages keep pip wheels
#  from falling back to source builds.
#      sudo apt update
#      sudo apt install -y build-essential git curl wget \
#                          libportaudio2 libportaudiocpp0 portaudio19-dev
#
#  ── STEP 3: Install Miniforge (conda + conda-forge by default) ──
#      wget https://github.com/conda-forge/miniforge/releases/latest/download/Miniforge3-Linux-x86_64.sh
#      bash Miniforge3-Linux-x86_64.sh -b -p ~/miniforge3
#      source ~/miniforge3/etc/profile.d/conda.sh
#      conda init bash
#      # Open a new shell or `exec bash` so `conda activate` is wired up.
#
#  ── STEP 4: Create the env + install Council ──
#  These commands mirror Sections B / C / D but on Linux Python 3.11

#      persistent across shells.

#  Keep `vault/` INSIDE the WSL filesystem (~/Council-Demo/vault/)
#  rather than under /mnt/c/Users/.../vault. WSL's 9p file-server
#  bridge is ~10x slower for many-small-file workloads than the
#  native ext4. The vault index walks 1000s of files; this matters.
#
#  If you already have a vault on the Windows side and don't want
#  to copy it, you can symlink:
#      ln -s /mnt/c/Users/<you>/Council-Demo/vault ~/vault

#  ── WSL-specific gotchas ──
#  - `nvidia-smi` works but `torch.cuda.is_available()` is False
#    → Your Windows NVIDIA driver is too old (need 535+ for cu124,
#      555+ for cu128). Update the driver on the Windows host
#      (NOT inside WSL), then `wsl --shutdown` from a Windows
#      PowerShell and reopen the Ubuntu shell.
#
#  - Tkinter window doesn't appear on Windows 11
#    → WSLg disabled. Confirm with: `wsl --version` — needs WSL 2
#      version 1.0+. Run `wsl --update` from Windows PowerShell.
#
#  - "OSError: libcuda.so: cannot open shared object file"
#    → The WSL distro is too old (pre-22.04 doesn't expose libcuda
#      via the GPU driver passthrough cleanly). Install Ubuntu-22.04
#      or 24.04 with `wsl --install -d Ubuntu-24.04`.
#
#  - `paramiko` / `cryptography` build fails with "linker not found"
#    → STEP 2 missing. Run `sudo apt install -y build-essential`.
#
#  - PyInstaller bundle (`council.spec`) — DON'T build inside WSL
#    if your target is Windows. PyInstaller produces ELF binaries
#    in WSL. Build the .exe in Windows native (Section B/C/D) and
#    use WSL only for dev runs / large-dataset testing.
#
#  - "Illegal instruction (core dumped)" on model load
#    The most common WSL crash. The prebuilt CUDA wheels for
#    llama-cpp-python (from abetlen's index) assume the host CPU
#    supports AVX2 + F16C. WSL inherits the Windows CPU feature
#    set, but a few configurations end up without one of those
#    flags exposed to the Linux side:
#       - Older CPUs that lack AVX2 entirely (pre-Haswell Intel,
#         pre-Excavator AMD).
#       - VMs nested inside Hyper-V where the hypervisor masks
#         feature flags from the guest.
#       - Some corporate-managed Windows installs that disable
#         hardware virt features via group policy.
#
#    Diagnose: in the WSL shell, run
#        grep -o 'avx2\|f16c' /proc/cpuinfo | sort -u
#    If both `avx2` and `f16c` print, the wheel SHOULD work — and
#    the crash is something else (read on). If either is missing,
#    that's the cause.
#
#    The app's GGUF loader now prints a CPU feature line at
#    startup, like:
#        [CPU] features include avx=True avx2=True f16c=True ...
#    If avx2=False appears, the next line will be a SIGILL warning.
#
#    Fix path 1 — rebuild llama-cpp from source WITHOUT AVX2:
#        pip uninstall -y llama-cpp-python
#        CMAKE_ARGS="-DGGML_AVX2=OFF -DGGML_F16C=OFF -DGGML_CUDA=ON" \
#            pip install llama-cpp-python --no-binary llama-cpp-python
#    The compile takes 5-15 min on the GPU sections. This produces
#    a wheel matched to your exact CPU + GPU.
#
#    Fix path 2 — if it crashed but `avx2` IS present, it's almost
#    certainly the CUDA wheel-vs-driver mismatch instead. The
#    Llama() constructor SIGILL'd inside a CUDA op. Verify with:
#        nvidia-smi                         # confirms host driver
#        python -c "import torch; print(torch.cuda.is_available(), \
#                                       torch.version.cuda)"
#    If torch.version.cuda is 12.4 but the driver shows CUDA 12.1,
#    downgrade torch to cu121 (Section B) — `cu124` needs driver
#    545+. Same logic for cu128 → driver 570+.
#
#    Fix path 3 — bypass GPU entirely as a fast sanity check:
#        export COUNCIL_GGUF_GPU_LAYERS=0
#        python council_gui_engine.py
#    If the app starts cleanly on CPU, the crash was definitely
#    in the GPU path (driver mismatch or CUDA op SIGILL). If it
#    STILL crashes on CPU, you're in fix path 1.

#  No CUDA drivers? Here's how to check, install, or skip
#  ─────────────────────────────────────────────────────────────
#  Sections B / C / D above all assume you have a working NVIDIA
#  driver. If you don't (or aren't sure), this section walks you
#  through the check, the install, and how to verify it's working.
#
#  KEY THING TO KNOW: you only need the NVIDIA DRIVER, not the
#  "CUDA Toolkit" or "CUDA SDK". PyTorch's and llama-cpp's CUDA
#  wheels bundle their own CUDA runtime libraries; the driver is
#  the only NVIDIA piece you have to install.
#
#  ── STEP 1: Check what you have ───────────────────────────────
#  Open a fresh terminal (cmd / PowerShell on Windows, bash on
#  Linux/WSL) and run:
#
#      nvidia-smi
#
#  Three possible outcomes:
#
#  (a) Command not found / "is not recognized as an internal or
#      external command"
#      → You have no driver installed OR no NVIDIA GPU. Go to
#        STEP 2.
#
#  (b) A table prints showing your GPU model and a "CUDA Version:
#      XX.Y" entry in the top-right
#      → Driver is installed. The "CUDA Version" line is the
#        MAXIMUM CUDA toolkit version your driver supports. Use it
#        to pick the section in STEP 3.
#
#  (c) Command exists but says "no devices found" / "couldn't
#      communicate with the driver"
#      → Driver is corrupted or doesn't match your GPU. Reinstall
#        the driver per STEP 2.
#
#  ── STEP 2: Decide what to install ────────────────────────────
#  If you have no NVIDIA GPU at all (Apple Silicon, AMD, Intel
#  integrated only) → use SECTION A (CPU only) above and ignore
#  the rest of this block. The app still works on CPU — just
#  slower inference.
#
#  If you have an NVIDIA GPU but no driver, install the driver
#  for your card from:
#
#      https://www.nvidia.com/Download/index.aspx
#
#  Pick "Game Ready Driver" (or "Studio Driver" — either works,
#  Studio is just slower-cadence and more stable). Choose your
#  exact GPU model + your OS + 64-bit. Download, run installer,
#  reboot. Then re-run `nvidia-smi` to verify the table prints.
#
#  Linux users: prefer your distro's package manager when possible
#  (e.g. `sudo apt install nvidia-driver-550` on Ubuntu 22.04+)
#  rather than the .run installer — apt-managed drivers survive
#  kernel updates cleanly.
#
#  ── STEP 3: Map your driver to a CUDA wheel section ───────────
#  Once `nvidia-smi` prints, look at the "CUDA Version: XX.Y"
#  number in the top-right of its output. This is the MAX CUDA
#  your driver supports, NOT the version you "have" — you can
#  always use a LOWER CUDA wheel than your driver supports.
#
#      Driver shows CUDA ≥ 12.1   → use SECTION B (cu121) for any
#                                   RTX 20/30-series / GTX 16xx /
#                                   MX450/550
#      Driver shows CUDA ≥ 12.4   → use SECTION C (cu124) for any
#                                   RTX 40-series / Ada workstation
#      Driver shows CUDA ≥ 12.8   → use SECTION D (cu128 nightly)
#                                   for RTX 50-series Blackwell

#  Driver version → "CUDA Version" line cheat sheet
#  (the number is the MAX CUDA supported, not the installed one):
#      Driver 525.xx → CUDA 12.1   → Section B
#      Driver 545.xx → CUDA 12.4   → Section C works
#      Driver 555.xx → CUDA 12.5   → Section C works
#      Driver 565.xx → CUDA 12.6   → Section C works (D when stable
#                                    cu128 wheels are available)
#      Driver 570.xx → CUDA 12.8   → Section D
#
#  Driver too old? Update it from the NVIDIA Download page above.
#  Updating the driver is a download + installer + reboot —
#  doesn't touch anything in your conda env.
#
#  ── STEP 4: Verify after install ──────────────────────────────
#  After running your chosen Section (B / C / D), the final
#  `python -c "import torch ..."` line in that section prints:

#      CUDA: True
#      all imports OK

#  If you see `CUDA: False`, something is off. Common causes:

#  ─────────────────────────────────────────────────────────────
#  Common conda+pip conflicts (and how to fix them)
#  ─────────────────────────────────────────────────────────────
#  Symptom: `import simplnx` fails with `_ARRAY_API not found` or
#           `numpy.dtype size changed`.
#  Cause:   pip upgraded numpy to 2.x; dream3dnx was built against 1.x.
#  Fix:     conda install -c conda-forge "numpy<2.3" -y
#
#  Symptom: `import simplnx` crashes with `HDF5 library version
#           mismatched error`.
#  Cause:   PyPI h5py and conda dream3dnx loaded different HDF5 DLLs.
#  Fix:     pip uninstall h5py -y && conda install -c conda-forge h5py -y
#
#  Symptom: Random `OMP: Error #15: Initializing libiomp5md.dll`.
#  Cause:   Two OpenMP runtimes loaded into one process.
#  Fix:     set KMP_DUPLICATE_LIB_OK=TRUE   (last-resort workaround)
#           or reinstall scipy/numpy from conda-forge to use MKL OpenMP.
#
#  Symptom: `DLL load failed while importing simplnx` (Windows).
#  Cause:   MSVC runtime mismatch between conda dream3dnx and a pip wheel.
#  Fix:     Microsoft Visual C++ 2015-2022 Redistributable — install
#           the x64 version from microsoft.com.
