# The Build tab: a chat beside the code (2026-10-29)

Andy asked for "a code IDE where I chat to a model that sits in the chat and
works on the code iteratively from my input, like ChatGPT". Agreed design
(proposal: https://claude.ai/artifact/99erUVDX6fLbmRXRwSBD1e):

- ONE Build tab: files left, editor middle, chat right. It replaces the Code
  and IDE tabs once step 5 lands; until then they stay.
- Model edits are shown as diffs the user accepts or rejects per hunk
  (Accept all for quick turns). Accepted edits go on a session branch in a git
  worktree, one commit per turn: Undo turn reverts one, Merge brings the
  session into the project (refused over uncommitted work, as today).
- Built next, before the plugin foundation and tab groups.
- The model may run the project's tests by itself, up to 3 rounds; anything
  else it wants to run waits for the user's click. Every run in the sandbox.
- Local, US-origin models only, picked from the detected GPU memory.

## Steps

Andy added four ideas from the Devin research on 2026-10-29 (the step
list, the plan card, stop when stuck, the grouped review); they are folded
into steps 3 and 4 below.


1. **Editor** (done): `council_qt/tabs/build.py`, `council_qt/widgets/code_editor.py`,
   `council_core/build_files.py`, `council_core/code_highlight.py`;
   tests in `tests/test_build_tab.py`.
2. **Chat, Ask mode** (done): streaming chat beside the editor that sees the open
   file and selection; changes nothing; conversation saved per folder.
   `council_core/build_chat.py`, `council_qt/widgets/build_chat.py`;
   tests in `tests/test_build_chat.py`.
3. **Edit mode** (done): `project_tools.edit_file`-style exact replacements shown as
   hunks with accept/reject; session worktree branch, commit per turn.
   `council_core/build_edits.py`, `council_core/build_session.py`; tests in
   `tests/test_build_edits.py`. Also:
   - **A step list under each reply**: a folded list of what the model did in
     that turn (files read, edits proposed, tests run), each with its result;
     clicking a step opens that diff or that output.
   - **A plan card with a confidence mark**: a request that touches more than
     one file first gets the files found, a short plan and a green, amber or
     red mark. Amber or red comes with up to three questions, and nothing is
     edited until the user answers or presses Go. One-file edits skip it. The
     mark is not the model's own score alone: Council checks that the files
     it names exist and the names it plans to call are in `code_map`
     (thresholds as in `confidence.py`).
   - **A grouped review before Merge**: the session's changes grouped by file
     and function, one plain line per group on what changed and why, lint and
     test warnings at the top; the chat can be asked about any group.
4. **Run and fix** (done): Run/Test through the sandbox (plan step A2+B3), "Fix this"
   sends the traceback, the model may run tests up to 3 rounds, Qt screenshot
   preview through `gui_check`. **Stop when stuck**: when a test round fails
   with the same error as the round before, or an edit is refused twice, the
   model stops (within the 3 rounds) and writes a short blocker: what it
   tried, the error, and what it needs from the user.
   `council_core/build_sandbox.py`, `council_core/_build_sandbox/`; tests in
   `tests/test_build_run.py`.
5. **Agent mode and models**: the Code tab's plan-and-run pipeline from the
   chat; model by VRAM with US coder entries (plan B6); retire Code and IDE.
   In two parts so Agent mode can be tried before anything is taken away:
   - **5a** (done): Agent mode and the Model box in the chat.
     `council_core/build_agent.py`, `council_core/build_models.py`,
     `council_qt/widgets/build_agent.py`; tests in `tests/test_build_agent.py`.
   - **5b**: the Code tab's remaining extras (Brief, Benchmark on history,
     the list of past jobs) in Build, then the Code and IDE tabs retired.

## How step 1 works

- Colours: Pygments over the WHOLE text (multi-line strings stay strings),
  spans painted per line by `CodeHighlighter`, recomputed 150 ms after typing.
- Files: opened as text (no binaries, <= 2 MB), encoding and CRLF kept, saved
  atomically, and Save asks before overwriting a file changed on disk.
- Unsaved buffers at the Council's close go to `<app dir>/build_unsaved/`,
  never over the file; the tab says so on its next open.
- Run: `python -u file` in the file's own folder with "Run with"'s Python
  (`python_envs`), `ide_trust` asks first, Stop kills it. In the sandbox
  since step 4.

## How step 2 works

- The model: `council_engine.local_chat` with the "coder" role (its slot, else
  the main model), temperature 0.2, the reply length from `token_budget`. It
  streams through `local_chat`'s new `token_callback`; the panel redraws every
  120 ms. Stop sets `should_stop`; the answer so far is kept, marked "(stopped)".
- What it is shown each turn (`build_chat.context_block`): the open file as
  edited (unsaved text included), lines numbered; a file over 24,000
  characters is cut to a window around the selection or cursor, and the model
  is told which lines it sees. The selected lines again, or the cursor's line.
  The last 60 lines of the last run's output when "Include the last run's
  output" is ticked, which a failed run ticks by itself.
- History: earlier turns, newest first, within 12,000 characters; the model
  is told how many earlier messages it is not shown.
- Kept per folder in `<vault>/.council_build/chats/<folder name>-<hash>.json`
  (a dot-folder, so the vault search skips it; the first version's
  `build_chats/` is still read) (atomic,
  last 200 turns); opening the folder again shows it. New chat clears it.
- Ask mode changes no file. "Copy code" copies the last answer's last code
  block; applying edits is step 3.

## How step 3 works

- The chat's mode box: Ask (answers only) or Edit (proposes changes). Edit
  mode uses `build_edits.EDIT_SYSTEM`: the model writes SEARCH/REPLACE
  blocks with a "Why:" line, or a PLAN block when the request needs more than
  one file or it is unsure. It sees the open file without line numbers (so
  it copies text, not numbers; "12| " prefixes it copies anyway are dropped),
  the other open files (30,000 characters in all) and the folder's code map
  (`code_map`, skipped for a folder of more than 4,000 entries, cached in
  `<vault>/.council_build/maps/`).
- Matching (`build_edits.resolve`): exact and unique, then ignoring trailing
  spaces, then one consistent indentation shift (the replacement is
  re-indented). Refused: in two places, not there (with the closest text),
  overlapping another block, outside the folder, an unreadable file. A
  refused block makes the chat ask the model ONCE more, by itself, for just
  those blocks; what still fails is shown as refused.
- Review: each edit under the reply as a diff with Accept / Reject; Accept
  all, Reject all, Apply accepted. Nothing changes until Apply, and a new
  message waits until the proposal is applied or rejected.
- Where edits land:
  - No session (any folder): into each file's editor as one undo step, NOT
    saved; Save writes them. Undo turn puts the editor text back.
  - Session (the folder is a git repository; "Start session"): a worktree on
    `council/build-<time>-<id>` in `<vault>/.council_build/sessions/`
    (a dot-folder, so the vault search skips it). The tab shows the
    session's copy; open files move over with their unsaved edits. Before
    each turn the user's own edits are committed as "Your edits", then the
    accepted edits as "Turn N: <request>". Undo turn = `git revert` of the
    newest turn (a conflict is aborted and said). Review and merge shows the
    grouped review, then `worktree.merge` (refused over uncommitted work in
    the project folder). End session throws the branch away. The record
    (`<id>.json` beside it) reopens the session after a restart.
- The step list ("▸ N steps" under an Edit reply, clickable): files read, the
  code map, each proposed edit and whether it was applied or rejected, the
  second request, what was applied, the commit, an undo. A step opens its
  file at its line; an edit's step shows its diff.
- The plan card: files, steps, Council's mark and why, the model's
  questions. The mark (`build_edits.mark`) starts from the model's
  CONFIDENCE (>= 80 green, > 40 amber, else red) and drops a level for a
  named file that does not exist (not marked "(new)") and for a `name()` the
  code map does not know; questions keep it amber at best. Go (button or
  link) sends "Go ahead with the plan." with the plan's files shown.
- The grouped review (`build_session.review_groups`): the session's diff
  against its start, by file and by the innermost def or class of each
  change (`-U0`, two lines of the file around each), one plain line per
  group ("Changed in `g` (+1 −2 lines): <the Why lines>"), lint findings
  (`tool_kit.lint`) and their groups first. "Ask about this" puts the
  group's diff in front of the next Ask-mode question.

## How step 4 works

- The sandbox (`build_sandbox.run`, light as agreed in D4):
  `council_core/_build_sandbox/` goes first on the child's PYTHONPATH (what
  was there stays after it, so the tests' own guards still load); its
  sitecustomize runs the one it shadows, then installs an audit hook that
  refuses connections, datagrams and name lookups off this PC (localhost,
  127.x and ::1 are allowed) and prints one line per refusal, and points
  stderr at stdout so a traceback lands in order. On Windows the child runs
  in `child_proc`'s Job Object (the tree dies with Stop, the time limit or the
  Council; a per-process memory cap: 2 GB Run, 4 GB Test); elsewhere its own
  session, killed as a group. No console window, stdin closed, a time limit
  (30 min Run, 5 min Test). Not covered: a program that is not Python, and
  what the code reads or writes on disk (`ide_trust` asks before Run; in a
  session the code runs in the session's copy). `council.spec` ships the hook
  folder as files.
- Test: `python -m pytest -q -p no:cacheprovider` with "Run with"'s Python in
  the folder, when it has tests (`has_tests`: test_*.py / *_test.py at the
  top or in tests/, conftest.py, pytest.ini, tox.ini, `[tool.pytest` in
  pyproject.toml); offscreen Qt, no dialogs. A missing pytest is said.
- Fix this (after a failed Run, Test or Preview): the chat in Edit mode with
  the file and the output. After a failed TEST, applying the fix runs the
  tests again by themselves (the only thing the model starts without a
  click), at most 3 rounds; each still-failing round asks for the next fix.
- Stop when stuck: the failure's signature (`build_sandbox.signature`:
  pytest's FAILED/ERROR lines, else the last exception line, with addresses,
  temp paths, timings and line numbers taken out) equal to the round before,
  or 3 rounds, or an edit that still does not match after the second
  request: the chat asks the model in Ask mode (`build_chat.STUCK`) for What
  I tried / The error / What I need from you, shown as "Council · stuck". A
  rejected proposal or a Stop ends the rounds too.
- Preview: the open file's first Qt widget class (`widget_classes`) built
  offscreen by `gui_check` from the folder; the picture and widget tree in a
  window, the summary in the output; an error enables Fix this.

## How step 5a works

- Agent mode (the chat's third mode) is the Code tab's pipeline
  (`code_agent.make_plan` / `run_job`) for the open folder:
  - The project is the folder's saved one (found by its folder), or a new
    one named after the folder, with pytest through "Run with"'s Python
    when it has tests; it is saved on the first plan. "Project…" edits it
    (test command, GUI checks, reference documents), "Agents…" the agents
    (`code_profiles`, the built-in "Qt app builder" among them).
  - The plan is a card under the reply, kept on the chat turn as data
    (`build_agent.plan_steps`), so it survives a restart. Each step can be
    left out or put back; writing again while the plan is open asks for a
    new plan with the first request plus "Change to the plan: …".
  - Go runs the kept steps on the job's own branch, in a worktree under the
    project's vault folder; the events arrive as the reply's step list. The
    reply then says how many steps were committed, with "Review and merge"
    (the branch's diff and commits in the review window) and "Discard"
    (asks first). Merge is refused over uncommitted work and waits for
    unsaved editor tabs to be saved; the open files are then read again.
  - A report-only agent answers with its report and changes nothing.
  - It needs a git folder and waits while an Edit-mode session is open.
- The Model box is the coder role's model (`model_slots`; Ask, Edit and
  Agent all answer as "coder", and the Models tab shows the same choice):
  - the installed models ranked for code on the detected GPU memory
    (`local_models.rank_for_role`: US-origin only, a full GPU fit before a
    bigger model that spills to RAM), the best marked ★; "Main model" puts
    the coder back on the Council's own model;
  - when nothing installed fits the card fully, the catalog's US code models
    that would (`model_catalog.for_vram(role="code")`) are named with the
    command that fetches one; the Council does not download it;
  - choosing writes `model_slots.json` atomically (the coder's own slot; the
    other roles keep theirs; a file it cannot read is left alone) and tells
    the engine to reload its map. Read on a worker the first time the chat
    is shown.
- Not added: new catalog entries for code-specialised models (Granite Code,
  CodeGemma). Their exact GGUF file names could not be checked from here,
  and a wrong name would send the user to a file that does not exist; add
  them once checked on a PC with internet.
