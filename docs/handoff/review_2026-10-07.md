This is for the Claude Code session on the **desktop** (branch `knowledge-graph`).

## 0. Do this first

The laptop's work is on its branch `merge/knowledge-graph`. It is **not pushed yet**.
After the laptop pushes it to `origin/qt-migration`:

```
git fetch origin
git checkout knowledge-graph
git merge origin/qt-migration
```

Do this merge **before** you edit any of these files again:
`council_core/knowledge_graph.py`, `council_core/kg_extract.py`,
`council_qt/tabs/connections.py`, `council_core/pi_setup/*`,
`council_qt/tabs/pi_setup_dialog.py`, `council_qt/tabs/apothecary.py`, `field_search.py`
and their tests. The laptop rewrote large parts of `seed()`, `merge()` / `unmerge()`
and `suggest_from_text()`. If you work on the old versions, the merge will conflict
badly.

The store's schema is now **v3**. The upgrade from v2 only adds two tables and one
index. A Council at v2 refuses a v3 store as "written by a newer Council", and it leaves
the store untouched. So after the merge, run only the merged code against a store that
the merged code has opened.

## 2. The user's decisions (2026-10-07), verbatim

For the Pi setup system (council_core/pi_setup/*, council_qt/tabs/pi_setup_dialog.py,
apothecary changes):

- **a.** MODEL PULL: "Allow it, only with a click" - an exception to "the Council never
  downloads models", for Pi setup only: the wizard names the US-origin model and its
  download size and pulls it on the Pi only after the user presses an explicit "Download on
  the Pi" button; never automatically during setup.
- **b.** OLLAMA INSTALL: "Pinned, checked release" - install ONE specific Ollama release
  whose checksum is recorded in the Council (download the release asset for linux-arm64 on
  the Pi, verify its sha256 BEFORE installing, refuse on mismatch); no 'curl | sh'.
  Updating Ollama = updating the Council's pinned version + checksum. The prepare phase finds
  the release data.
- **c.** PI LOGIN: "Turn password login off" - once the Council's key login is VERIFIED
  working, SSH accepts keys only (an sshd_config.d drop-in setting PasswordAuthentication
  no, KbdInteractiveAuthentication no; validate with sshd -t before reloading; never lock
  the user out: only after a successful key login in the same session); the wizard shows
  how to turn passwords back on. (NOPASSWD sudo for the Council's key session stays as
  built.)
- **d.** "Remove Wi-Fi key after boot": after first boot and a successful key-login
  provision, make sure the Wi-Fi connection persists in NetworkManager (nmcli shows the
  profile), stop cloud-init from re-rendering the network
  (/etc/cloud/cloud.cfg.d/99-disable-network-config.cfg with network: {config: disabled}),
  and scrub the seed's network-config (and anything else with the PSK) on the boot
  partition.
- **e.** "Check image before erasing": the image file's checksum (decompressed
  extract_sha256, and size) is verified BEFORE the elevated write erases the card; the
  hash/size/format belong to the FILE actually chosen (not the combo selection); a file not
  in the official list gets no assumed hash/format (the helper detects the format).
- **f.** "Confirm disks with files": any USB disk that already holds files (a non-empty
  filesystem on any partition) needs a second, explicit confirmation that names what is on
  it (volume labels, used space) before it can be chosen.
- **g.** "Faster graph rebuilds": knowledge-graph rebuilds skip documents whose content hash
  is unchanged and commit in batches so a long rebuild can resume.
- Also keep: reading "Bob, Alice" under a single-person label as one person (Last, First)
  - the current behaviour.

### How each one was built

- **a.** `pi_models.describe()` gives the maker and size, for example "llama3.2:3b (Meta,
  US) — about 2.0 GB to download on the Pi". The sizes come from the Ollama library;
  llama3.1:8b is the only one measured here. `setup.download_model` → `remote.pull_model`
  runs only from the dialog's "Download on the Pi" button, and it refuses non-US models.
  `Outcome.model_pending` tells the dialog to offer the button.
- **b.** Four constants in `remote.py` (`OLLAMA_PIN_VERSION` = 0.35.0, `OLLAMA_PIN_URL`,
  `OLLAMA_PIN_SHA256` = `cb627d33…ec3bd09374`, `OLLAMA_PIN_SIZE` = 1,550,231,393).
  - One bash step downloads the file to `/var/tmp`, checks its size and `sha256sum -c`, and
    only then removes the old `lib/ollama` and unpacks with `tar --zstd`.
  - A preflight step checks for a 64-bit OS, zstd (installing it with apt if missing),
    that github.com is reachable, and that 6 GB is free.
  - Ollama's service account and unit are made the way install.sh makes them.
  - The check step waits for `/api/version` to say 0.35.0.
- **c.** `/etc/ssh/sshd_config.d/00-council-keys-only.conf`.
  - The file starts with `00-` because sshd keeps the first value it reads, and
    cloud-init's `50-cloud-init.conf` may say yes.
  - The setup runs `sshd -t` before the reload (a refused file is removed), then
    `sshd -T`.
  - It then proves that a new key login works. If it does not, password login is turned
    back on over the session that is still open.
  - It then asks the running sshd which login methods it offers ('none' auth).
  - If anything fails after the drop-in is written (`sshd -t`, the reload, the
    read-back), an EXIT trap removes it again. Reloads are `reload-or-restart`.
  - The "Switch to key login" button in the Apothecary tab does this too.
  - `remote.password_login_help()` gives the undo.
- **d.** This is the second-to-last provisioning step. It acts only on a network-config
  that the Council wrote, and only when nmcli shows a Wi-Fi profile stored on the Pi
  itself: a keyfile, or cloud-init's netplan YAML. NetworkManager's copy of a netplan
  profile lives in `/run`. If there is no such profile, the card is left alone and the step
  fails. Before network-config is replaced, its bytes are zeroed where they are on the
  FAT partition (`shred -n 0 -z -x`); the first step does the same to user-data, and the
  legacy firstrun.sh zeroes itself.
- **e.** `writer.check_image` runs in the elevated helper **before** `Clear-Disk`.
  - The disks are listed again **after** the check, and every rule (identity,
    eligibility, the files the user agreed to) runs on that listing just before
    `Clear-Disk`.
  - A file that is not in the list has no hash to check, but it is still checked against
    the card's capacity.
  - `images.release_format` is gone. When the format is unknown, the job carries the
    first-boot files for both formats, and the helper uses the one the written card shows.
  - `setup.note_written` drops the pre-made host key from the pending record of a legacy
    card.
- **f.** `disks.Disk.contents()` / `holds_files`. Each SD / MMC / USB volume's top
  folder is listed (by its volume path, so a volume with no letter too); any entry
  except System Volume Information counts. A volume that cannot be listed, a partition
  Windows cannot read, and a RAW disk may hold files. A Microsoft Reserved partition
  does not count.
  - The dialog asks a second question that names each volume, or a partition Windows
    cannot read. Offscreen, with nobody to answer, the answer is no.
  - The yes is kept with the card's identity AND the contents it named.
    `prepare_new_pi` and job.json carry those contents, and the elevated helper refuses
    a card that holds anything else.
  - **The rule applies to SD-bus cards too, not only USB**, because a camera card's photos
    are the same loss. Tell the user, in case they meant USB only.
- **g.** `seed()` now has two phases.
  - **Reading.** Each document's records and text lines are cached in `doc_cache`, keyed by
    content hash and by a reader signature. The signature covers the confirmed rules, the
    bytes of the reading code, and the versions of the reader libraries. This phase commits
    every 50 documents or every 5 s.
  - **Building the graph.** This happens in one transaction from the cache, and gives the
    same graph as a fresh build.
  - The cached text of a deleted or unreadable document goes in the same rebuild, and
    `export_json` never includes the cache. The store runs with
    `PRAGMA secure_delete = ON`, so that text is overwritten in the file, not only
    unlinked.
- **Last, First** is unchanged. `person_display` and `named_in` were not touched.
